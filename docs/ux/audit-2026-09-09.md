# Technical audit - 2026-09-09

`/impeccable audit`, native (React Native 0.86, iOS + Android). Code-level only: no simulator or
device was booted for this pass, so every claim below is traced to a file and line, a computed
number, or a read of the RN/Android source that produces the behaviour. Nothing here is a
screenshot impression.

Baseline at time of audit: `tsc --noEmit` clean, `eslint` 0 errors / 211 warnings, `jest` **998
tests in 114 suites, all passing**.

## Platform Conformance Verdict - **PASS**

This does not read as a ported website. Evidence, not impression:

- Navigation is a real `createNativeStackNavigator`, not a custom router (`AppNavigator.tsx:390`).
- The iOS left-edge back gesture is alive. Stack screens get it natively; the three AppShell-level
  routes that sit outside the stack get a hand-built equivalent with correct activation offsets and
  a velocity commit (`EdgeSwipeBack.tsx:53-70`), and Android's system Back is routed rather than
  hijacked (`EdgeSwipeBack.tsx:41-47`).
- Safe-area insets are not guessed: `useHeaderTop` and `useContentBottom` derive from
  `useSafeAreaInsets`, and both carry a comment explaining the bug that hardcoding caused.
- Predictive Back works. RN 0.86 registers an `OnBackPressedCallback` on the dispatcher
  (`ReactActivity.java:31-63`), so `BackHandler` survives targetSdk 36 - verified in the RN source,
  not assumed.
- Platform idioms are present and correct: pull-to-refresh, swipe actions, bottom sheets, a single
  FAB with one primary action, a snackbar for transient feedback, haptics on selection.

Two deliberate departures, both defensible and both consciously defended in-repo:

- **Custom dialogs instead of `Alert.alert`**, enforced by a test with no allowlist
  (`__tests__/theme/noSystemAlert.test.ts`). The committed design world wins over the platform
  default here, and `Dialog.tsx` reimplements the accessibility contract it displaces
  (`accessibilityViewIsModal`, a heading role, safe dismiss). Accepted - but see §P2-10, where the
  five sibling overlays did not get the same treatment (all five do since 2026-09-14).
- **A custom SVG icon set** rather than SF Symbols / Material Symbols. Correct for one brand across
  two platforms; the set is internally consistent and tiered (`iconTiers.tsx`).

## Detailed findings

### P0 - fix immediately

#### P0-1 · Every avatar monogram fails contrast in dark mode

- **Location** `src/theme/Avatar.tsx:49`, ink from `src/theme/theme.ts` (`darkTheme.onBlue`)
- **Category** Accessibility / Theming
- **Guideline** WCAG 2.1 SC 1.4.3 (Contrast, Minimum) - AA requires 4.5:1

`Avatar` paints its monogram with `theme.onBlue`. In dark mode `onBlue` is `#1A1611`, a near-black
ink. Measured against the six avatar hues:

| Hue | Light (white ink) | Dark (`#1A1611` ink) |
|---|---|---|
| `#2A5C9A` brand blue | 6.78 | **2.65** |
| `#0E6E6E` teal | 6.04 | **2.98** |
| `#5A4CA8` purple | 6.92 | **2.60** |
| `#1B6E52` green | 6.18 | **2.91** |
| `#8A5A18` bronze | 5.90 | **3.05** |
| `#1E4E80` deep blue | 8.55 | **2.11** |

All six are below AA; five are below the 3:1 floor that even large text gets. The avatar appears on
every inbox row, every search result, the detail postmark card, the box switcher and the re-auth
identity tile - so in dark mode the app's most repeated element is illegible.

Both files document the opposite. `avatar.ts:4` - *"every colour is dark enough that the white
initial stays ≥4.5:1 (WCAG AA) in both light and dark themes."* `Avatar.tsx:3` - *"dark mode
strengthens the tint and lightens the monogram so it stays ≥4.5:1 (AA)."* It also contradicts the
confirmed pixel-parity decision that avatars are solid fills with white initials.

- **Root cause** Commit `c5dc3c5` ("dark mode was failing its own AA promise on every primary
  button") correctly changed dark `onBlue` from white to near-black ink so that labels on
  `theme.blue` reach 6.79:1. `onBlue` means *"ink that sits on `theme.blue`"* - but six sites were
  consuming it as *"white"*. Three of them sit on a ground that is not `theme.blue`.
- **Recommendation** Introduce a distinct token for "white in both appearances"
  (`onSolid` / `onBrandSolid`) and point `Avatar`, `EmblemIcon` and the `Toggle` knob at it. Do not
  fix this by reverting `onBlue` - that re-breaks every primary button.
- **Suggested command** `/impeccable colorize`

#### P0-2 · The same collision, two more sites

- **Location** `src/theme/iconTiers.tsx:97` (`EmblemIcon`), `src/theme/Toggle.tsx:56`
- **Category** Accessibility / Theming

**`EmblemIcon`** - its own docstring reads *"a 44px **white** glyph knocked out of a 96px solid
brand-blue tile"*, and `brandTile`'s token comment reads *"fixed in both modes so a white glyph
stays AA."* In dark mode the glyph renders `#1A1611` on the fixed `#2D6CB5`: **3.36:1**, below AA.
White would be 5.35:1. This is the compose "message sent" confirmation - the screen that tells a
user their legal mail went.

**`Toggle` knob** - documented as *"a near-white knob that slides between edges."* In dark mode it
is near-black. Knob against the ON track is fine either way (6.78 / 6.79), but the knob inverts its
appearance between themes, which nothing in the design asks for.

- **Recommendation** Same token fix as P0-1.
- **Suggested command** `/impeccable colorize`

#### P0-3 · The contrast test cannot catch any of this

- **Location** `__tests__/theme/contrast.test.ts:45-58`
- **Category** Accessibility

The suite asserts twelve foreground/background pairs. `onBlue` appears in exactly one of them -
`['onBlue on blue', t.onBlue, t.blue]` - so the token is checked against the single ground where it
is correct, and against none of the three where it is not. The file's own header explains that a
palette *"is edited by eye and a number that used to pass is exactly the thing nobody
re-measures"*; the same is true of a ground that was never listed.

- **Recommendation** Derive the pair list from usage rather than by hand. At minimum add:
  `onBlue`/`brandTile`, `onBlue` against each of the six `AVATAR_COLORS`, `onBlue`/`trackOff`,
  and `gold`/`bg` + `gold`/`surface` at the 3:1 non-text floor.
- **Suggested command** `/impeccable harden`

### P1 - fix before release

#### P1-4 · Android's system navigation bar ignores the in-app theme

- **Location** `AndroidManifest.xml:41`, `App.tsx:33`; behaviour from
  `react-native/…/views/view/WindowUtil.kt:164-200`
- **Category** Conformance / Theming
- **Guideline** Material 3 - edge-to-edge with window insets

targetSdk is 36, so edge-to-edge is enforced and RN calls `enableEdgeToEdge()`, which sets
`insetsController.isAppearanceLightNavigationBars = !isDarkMode` where `isDarkMode` comes from
`Configuration.UI_MODE_NIGHT_MASK` - **the OS appearance**. The app's own `themeMode`
(light / dark / system) never reaches it. `StatusBar barStyle` is driven correctly from `isDark`
(`App.tsx:33`); the navigation bar has no equivalent.

Two failures follow:

1. **In-app theme ≠ OS appearance.** Choose Light on a dark phone and the gesture pill/icons stay
   light over `#F4EEE2` paper. Under gesture navigation Android applies no contrast scrim, so the
   handle is effectively invisible.
2. **A live OS flip never updates it.** `android:configChanges` includes `uiMode`, so the Activity
   is not recreated, so `enableEdgeToEdge()` - called once from `ReactActivityDelegate` - never
   re-runs. Even in "system" mode the whole app repaints and the nav bar keeps the stale appearance
   until the process restarts.

- **Recommendation** Drive `isAppearanceLightNavigationBars` from the app's resolved `isDark`,
  reactively - a small native module or `react-native-edge-to-edge`'s `SystemBars`, called from the
  same place `StatusBar` is set.
- **Suggested command** `/impeccable adapt`

#### P1-5 · No width adaptation anywhere, and Android 16 no longer lets the app opt out

- **Location** whole `src/` tree; `ios/…/Info.plist:46-49`; `android/build.gradle:6`
- **Category** Adaptivity
- **Guideline** Material 3 - navigation matched to window size class

`useWindowDimensions` appears **zero** times in the codebase. There are no size classes, no
breakpoints, no landscape variants. Two consequences:

- **iOS** is portrait-locked (`UISupportedInterfaceOrientations` = Portrait) and iPhone-only since
  `07d62fe`. Defensible, and consistent.
- **Android** does not match. No `android:screenOrientation` is declared and `configChanges`
  includes `orientation|screenLayout|screenSize`, so the app rotates and resizes freely - into a
  layout that has no landscape design. Worse, **targeting SDK 36 means orientation, resizability
  and aspect-ratio restrictions are ignored on screens ≥600dp**, so on a tablet or an unfolded
  foldable the app is displayed landscape and resizable whether or not it declares otherwise. What
  ships there today is a stretched phone UI.

The only content constraints in the tree are a handful of `maxWidth` values (240–420) on empty
states and dialogs - enough to keep prose readable, nowhere near a large-screen layout.

- **Recommendation** Decide the Android large-screen position explicitly. Minimum viable: cap the
  main content column and centre it above ~700dp so a tablet stops showing 900px-wide list rows.
  Full answer: a navigation rail and a list/detail split at expanded width.
- **Suggested command** `/impeccable adapt`

#### P1-6 · Fixed-height containers clip their own text at large font sizes

- **Category** Accessibility
- **Guideline** WCAG 2.1 SC 1.4.4 (Resize Text); HIG Dynamic Type; Material sp units

RN scales both `fontSize` and `lineHeight` by the system font scale (verified:
`TextAttributes.kt:75-89` - `effectiveLineHeight` goes through `toPixelFromSP`). Container heights
in dp do not scale. Nine containers set a fixed `height` and wrap scaling text:

| File:line | Height | Content |
|---|---|---|
| `DeadlineSuggestion.tsx:99` | 40 | `BodyStrong` 14 - accept button |
| `DeadlineSuggestion.tsx:119` | 40 | `BodyStrong` 14 - dismiss button |
| `MessageDetail.tsx:609` | 40 | `BodyStrong` 14 + `Caption` |
| `MessageDetail.tsx:1039` | 46 | `BodyStrong` 14 |
| `MessageDetail.tsx:1106` | 40 | `BodyStrong` 14 + `Caption` |
| `MessageDetail.tsx:1324` | 40 | `Value` |
| `ComposeScreen.tsx:841` | 34 | `Value` |
| `ComposeScreen.tsx:1222` | 44 | `Title` |
| `SearchScreen.tsx:134`, `LicencesScreen.tsx:123`, `ComposeScreen.tsx:889` | 44 / 46 | `Input` |

`SettingsScreen.tsx:122` already carries the correct pattern and the reasoning for it - *"minHeight,
not height: at a large system font size the Bricolage title is taller than the bar the design drew
for it, and a fixed 54 clips its descenders instead of growing."* Commit `4b4bc53` applied that to
two bars. The nine above did not get it.

- **Recommendation** `minHeight` throughout, plus a font-scale render test - none exists today
  (`grep fontScale __tests__` returns nothing).
- **Suggested command** `/impeccable harden`

#### P1-7 · Eight screens hand-roll the header that exists to stop exactly that

- **Location** `src/theme/ScreenHeader.tsx` vs. `SettingsScreen.tsx:118`, `ComposeScreen.tsx:484`,
  `ReauthForm.tsx:74`, `LoginFlow.tsx:297`, `OtpForm.tsx:105`, `AddBoxForm.tsx:128`,
  `SearchScreen.tsx:99`
- **Category** Conformance / design-system integrity

`ScreenHeader.tsx:1-5` names its own consumers: *"the design draws ONE header bar and repeats it
verbatim across every stack screen (compose, search, settings, add-box, credentials, OTP, mobile
key, reauth) … **One component so those copies can't drift** (constitution V - visual
consistency)."*

`ScreenHeader` has exactly **one** consumer: `SubScreen.tsx:35`. All eight named screens build
their own, and they have drifted:

| Screen | Bar sizing | Pad L / R | Gap | Chevron | Title |
|---|---|---|---|---|---|
| `ScreenHeader` (canonical) | `minHeight 54` | 6 / 6 | - | 44 | `Title` 18/23 |
| SettingsScreen | `minHeight 54` | 6 / 6 | 0 | 44 | `Heading` 18/23 |
| ComposeScreen | `minHeight 54` | 6 / 6 | 0 | 44 | `Title` 18/**22** |
| ReauthForm | `paddingBottom 12` | 6 / **16** | 4 | 44 | `Heading` 18/23 |
| LoginFlow | `paddingBottom 12` | 6 / **16** | 4 | 44 | `Heading` 18/23 |

Four distinct bar geometries, two chevron sizes, and a title line box that is 22 in compose and 23

#### P1-8 · The unread dot is 2.17:1 and it is the only unread signal

- **Location** `MessageList.tsx:1240` (`ReceivedRow`), `MessageList.tsx:1111` (`SentRow`)
- **Category** Accessibility
- **Guideline** WCAG 2.1 SC 1.4.11 (Non-text Contrast) - 3:1

A 7×7 dot in `theme.gold` on `theme.surface`. Light mode measures **2.17:1** (bg: 1.91:1); dark
mode is fine at 6.90:1. `ReceivedRow`'s own comment states the design intent: *"Read/unread is
signalled by the gold dot alone, not by thinning the sender."*

Screen-reader users are covered - `receivedRowLabel` carries `unread` into the row label, and
`31b5deb` fixed exactly that. A sighted low-vision user has nothing else.

- **Recommendation** Either lift the light-mode `gold` used for indicators to ≥3:1 on paper, or give
  the dot a second cue (size, a ring, or the row's left edge). Same call applies to the FAB, which
  sits at 1.91:1 against `bg` and leans on its drop shadow for a boundary.
- **Suggested command** `/impeccable colorize`

### P2 - fix in the next pass

#### P2-9 · No `keyboardAppearance` on any input

- **Location** all 16 `<Input>` / `<TextInput>` sites
- **Category** Theming / Conformance

`grep keyboardAppearance src` returns zero. On iOS the keyboard follows the OS appearance, so an

- **Location** `Dialog.tsx:100` has `accessibilityViewIsModal`; `BoxSwitcherSheet.tsx`,

`a0b6987` fixed the dialog and documented why. The five siblings present the same way - a

Related, smaller: `BoxSwitcherSheet.tsx:117` and `TermPicker.tsx:141` set `accessibilityLabel`

- **Suggested command** `/impeccable harden`

*Closed 2026-09-14.* The inert labels went in the first pass, and `BoxSwitcherSheet` and

#### P2-11 · No memoization on virtualized rows

- **Location** `MessageList.tsx:627` (`const now = Date.now()`), `:860` (inline `renderItem`),
  `:1043`/`:1195`/`:1292` (`AttentionCard`, `ReceivedRow`, `SentRow`)
- **Category** Performance

`React.memo` appears **zero** times in the tree. `renderItem` is an inline arrow, and `now` is
recomputed on every render of `MessageList`, so any parent state change (`syncing`, `refreshing`,
reminders arriving, folder switch) re-renders every mounted row - each of which builds an `Avatar`,
a `TermChip` and one or more `react-native-svg` nodes.

Virtualization caps the blast radius at the render window, so this is not a stall. It becomes one
on a years-old box, which the app explicitly supports (`groupByDate.ts:2` - *"even a years-long box
stays scannable by time"*). No list tuning props are set anywhere: no `initialNumToRender`,
`windowSize`, `maxToRenderPerBatch` or `removeClippedSubviews` on the `SectionList` or the search
`FlatList`.

- **Recommendation** `React.memo` the three row components, hoist `renderItem` behind
  `useCallback`, and lift `now` to state that changes only when it must. Measure before tuning
  window props.
- **Suggested command** `/impeccable optimize`

### P3 - polish

#### P1-12 · `hitSlop` typed by hand at 22 of 27 sites - two of them below the floor

`touchTarget.ts:10-13` states the rule: *"The point of computing the slop instead of typing it is
that the two numbers stay tied. Resize the switch and its touch area follows; type `hitSlop={10}`
beside it and it does not."* Five sites use `touchSlop()`; twenty-two type `6`, `8` or `10`.

**Correction (added while fixing).** This entry first said every one of them cleared 48dp. That was
generalised from a sample of five back-chevrons; measuring all twenty-two found **two that did not**:

| Site | Drawn | Slop | Target |
|---|---|---|---|
| `AddBoxForm.tsx:286` - the "?" beside *Prostředí* | 18×18 | 10 | **38×38** |
| `ComposeScreen.tsx:867` - remove an attachment | 30×30 | 6 | **42×42** |

So this was a P1, not a P3, and it is the finding's own point made twice over: a hand-typed slop is
correct only by luck, and the two that were unlucky were invisible until the numbers were added up.
All twenty-two now derive from the drawn size through `touchSlop()` or `textSlop()` - but not in one

*Closed 2026-09-14.* Those five now derive too, and `__tests__/theme/noTypedHitSlop.test.ts` scans

#### P3-13 · Launch shows the OS appearance before the chosen one

`SettingsProvider` reads `themeMode` from the encrypted SQLite table and gates on `ready`; until it
resolves, `themeMode` is `'system'`, so `App.tsx:39` paints the blank frame in the **OS** scheme.
Android's window background is `Theme.AppCompat.DayNight.NoActionBar`, which does the same. A user
who chose Light on a dark phone sees dark splash → dark blank → light app on every cold start.

#### P3-14 · `Dimensions.get` captured at module scope

`EdgeSwipeBack.tsx:22` reads `SCREEN_W` once at import. Inert today (that pan runs on iOS only, and
iOS is portrait-locked), but it is stale on any Android rotation and is the wrong pattern to leave
in place if P1-5 is addressed.

0 errors. Predominantly `react-native/no-inline-styles` firing on `boxShadow` strings, which is
current RN 0.86 practice rather than a defect. Worth a targeted rule adjustment so the count stops

## Patterns & systemic issues

1. **A semantic token was narrowed without re-checking its consumers.** `onBlue` went from "white"
   to "ink on `theme.blue`"; three of six consumers were never on `theme.blue`. The failure mode is
   silent because the token name still reads correctly at every call site (P0-1, P0-2).
2. **Shared components exist and are not adopted.** `ScreenHeader` (1 of 9 consumers),
   `touchSlop` (5 of 27), `accessibilityViewIsModal` (1 of 6). In each case the shared thing was
   written *first*, with a comment explaining the drift it prevents, and the drift happened anyway.
3. **Docstrings assert measured properties that nothing measures.** `avatar.ts` promises ≥4.5:1 in
   both themes; `iconTiers.tsx` and `theme.ts` promise a white emblem glyph; `Toggle.tsx` promises a
   near-white knob. All three are false in dark mode today. The pattern that works is already in the
   repo - `contrast.test.ts` turns a header sentence into an assertion - it is just under-applied.
4. **iOS is constrained, Android is not, and only iOS was designed for.** Portrait-lock and
   iPhone-only on one platform; free rotation, multi-window and forced large-screen resizability on
   the other, with the same phone-portrait layout serving both.
5. **System chrome is themed on one edge only.** The status bar follows the app theme; the Android
   navigation bar and the iOS keyboard follow the OS.

## Positive findings

Worth protecting, and worth copying into whatever gets built next:

- **998 tests, 114 suites, green, in 11 seconds.** Including mechanical guards that catch classes of
  regression rather than instances: `noSystemAlert.test.ts` scans the whole tree with no allowlist,
  `check-no-raw-hex.sh` reports **zero** raw hex literals outside the sanctioned palette files, and
  `contrast.test.ts` computes ratios instead of trusting them.
- **`ui.tsx`'s `pressable()` wrapper** fixes a Tamagui/VoiceOver defect once, at the primitive, for
  48 press targets across 23 files - with the reasoning written down so the next `<XStack onPress>`
  is correct without anyone knowing the history. This is the right altitude for a fix.
- **Reduce Motion is honoured in nine components**, and honoured *thoughtfully*: `PressScale`
  drops the shake but keeps the warning haptic and the focus move, so the refusal survives without
  motion. Reduce Transparency is handled too (`useScrim.ts`), which almost nothing ships.
- **The scrim maths.** Compositing a dark scrim over a dark ground and measuring it, because
  *"eyeballing a dark scrim on a dark screen is exactly the judgement a person cannot make."*
- **`PressScale`'s busy-vs-blocked distinction.** A disabled `Pressable` eats the touch, so the
  screen never learns someone tried; splitting the two at the primitive is a real UX insight, not a
  style preference.
- **Keyboard handling is genuinely worked out** - `KeyboardAwareScrollView` documents the
  iOS/Android split *and* the double-adjust trap when a `KeyboardAvoidingView` is also present.
- **`useHeaderTop` / `useContentBottom`** turn safe-area insets into one shared rhythm and record
  the bug that hardcoding caused.
- **Typography resolves the actual font face per weight** (`faceForWeight`) - the 4-style-family
  trap that silently renders every weight identically on Android, solved once.
- **The Android manifest removes four Notifee permissions it does not use**, with the Play policy
  consequence written out. Rare discipline.

## Closed 2026-09-14 - the rest of P2-10 and P1-12

### Overlay focus (P2-10)

`AliasEditor.tsx` (rename a box), `BoxOverflowMenu.tsx` (Přejmenovat / Odebrat) and `TermPicker.tsx`
(the Termín sheet) now set `accessibilityViewIsModal` on their card. With `Dialog.tsx`,
`BoxSwitcherSheet.tsx` and `ComposeScreen.tsx`'s paid-send sheet that is six overlays of six.

The fix copies the two overlays that already had it, and each platform is contained by a different
thing. `accessibilityViewIsModal` is iOS-only: a transparent `Modal` is presented
`UIModalPresentationOverFullScreen` (`RCTModalHostViewComponentView.mm`), so the screen that
presented it stays in the hierarchy, and the card's prop is what is meant to keep VoiceOver off it.
Android has no such prop and needs none - read in the RN 0.86 source, `ReactModalHostView` builds
each `Modal` as a `ComponentDialog`, a window of its own, and clears `FLAG_NOT_FOCUSABLE` once it is
shown - so the three components keep their `Modal` and add nothing Android-specific.

One thing the source cannot settle, found in review: Apple documents `accessibilityViewIsModal` as
hiding the *siblings* of the view that sets it, and every card here is the only child of its
wrappers. Whether a card-level prop really fences out the presenting screen is therefore a VoiceOver
question, and it is the same question for all six overlays - `Dialog.tsx`, which set the pattern,
included; nothing in this audit walked any of them with VoiceOver.

`__tests__/theme/overlayFocus.test.tsx` renders each overlay - the ⋯ menu once opened, and the
switcher with the menu and then the rename editor opened on top of it - and asserts the shape of
containment rather than the presence of a prop: exactly one container marked modal per `Modal`,
nothing a screen reader can land on outside it, and no accessibility element between the `Modal` and
the card (on iOS an element is a leaf and would swallow the card). Cases: `overlays contain the
screen reader › the alias editor`, `› the ⋯ box menu, once it is open`, `› the reminder picker`,
`› the box switcher, and the menu and editor that open on top of it`, plus `› reports a button left
outside the fence, and a wrapper that swallows the card`, which proves the checker itself. A source
scan, `every Modal in the app › marks its content modal`, reads every `<Modal>` element under `src/`
from the TypeScript syntax tree and fails when nothing inside that element sets
`accessibilityViewIsModal` to true - the net for overlays no render test reaches. Its first version
counted the two words per file, which passed a prop set to `false` or placed beside the `Modal`;
`› is judged by what the Modal holds, not by what the file mentions` now proves it against both and
against a nested `Modal` left unmarked. Against the pre-fix screens the four render cases and the
scan fail; the dialog case and the checker's own self-tests pass either way, as they must.

## One defect the audit missed, found only by running it

**The search field never focused on open.** `mInputShown=false` on entry; `true` only after a tap -
on the one screen whose entire purpose is typing.

Not a regression from the header refactor: the pre-refactor `SearchScreen` was restored onto the same
emulator and behaved identically. It had simply never been looked at. And `SearchScreen` carried a
comment asserting the opposite - *"The field `autoFocus`es, so the keyboard is up before the first
result exists"* - which is the fourth docstring in this codebase found stating a property nothing
verified.

The root cause is two-part, and neither half is timing alone:

1. **Tamagui's `Input` does not forward `autoFocus` to the native `TextInput` at all.** `OtpForm` had
   already discovered this on an iPhone in August, proved it with a render test, and worked around it
   locally with a 120 ms timeout - where it cost more than a keyboard, because iOS offers its
   Security Code AutoFill suggestion above a *focused* field and there was none.
2. **A focus request made during a stack push is dropped.** Even focusing imperatively on mount
   fights the transition; the keyboard can appear and immediately leave.

Two screens had one problem and two different answers, which is exactly how the next screen gets a
third. Extracted as `src/theme/useAutoFocus.ts`, which prefers the native stack's own `transitionEnd`
(the precise signal rather than a guess at an animation's length) and falls back to a timeout for a
screen mounted outside a navigator, which the sign-in flow is. `InteractionManager`, the usual recipe,
is deprecated in RN 0.86 and says so at runtime. Verified: `mInputShown=true` on open.

That is the audit's own central lesson, arriving one more time: a shared thing written once, adopted
once, and drifted around.
